## Answer

On paper our conventions are at or above current best practice. The logging and comment standard matches the Python logging HOWTO, PEP 8, Google style and the Claude Code hooks docs almost line for line. The repo's own enforcement lags the paper, and in four places the repo contradicts our own "no silent failure" rule:
- CI's Bandit job can never fail (`|| true`).
- The secrets skill's TruffleHog hook can never block (it omits `--fail`).
- The `senior-secops` scanner always reports zero findings.
- Ruff runs on `src/` only, so the `tests/` and `scripts/` policy in `pyproject.toml` is dead config.

The biggest best-practice gaps are:
- **Supply chain:** no lock check, no dependency audit, no update bot, no repo secret scan.
- **Bash:** `set -e` caveats are undocumented, and the ShellCheck checks that catch them are off.
- **Skills:** six prompt files exceed the 500-line limit, frontmatter keys are silently ignored, and there are no behavioural evals.

Most fixes can be enforced mechanically (Ruff, ShellCheck optional checks, `uv sync --locked`, `uv audit`, gitleaks, Dependabot, and an extended frontmatter pytest).

### 2. Bash

| Area | Our convention (cite) | Best practice (cite) | Verdict |
|---|---|---|---|
| Strict mode | `set -Eeuo pipefail` + ERR trap (`bash-defensive-patterns/SKILL.md:23-35`; `logging-and-comments/references/bash.md:11`) | BashFAQ/105 lists the gaps: `if`/`&&`/`\|\|` contexts are "immune"; functions called as conditionals lose `set -e`; command substitution unsets it "unless inherit_errexit is set"; `local var=$(…)` masks the status; pipefail can fail `cmd \| head`. Its maintainers conclude "handle errors properly and not rely on the unreliable set -e" (https://mywiki.wooledge.org/BashFAQ/105). `inherit_errexit`: "command substitution inherits the value of the errexit option" (bash 5.3 man page) | **Weakness.** We present strict mode as "Exit on any error" (`bash-defensive-patterns/SKILL.md:33`) with no caveats. **Add:** a caveats block, `shopt -s inherit_errexit`, and "never `local x=$(cmd)`; declare, then assign" |
| Strict-mode drift | The skill says `-Eeuo` | — | 17 of 24 tracked `.sh` use `set -euo pipefail` (no `-E`, so ERR traps don't fire in functions); 2 use `-Eeuo`; 3 use only `set -u`; 2 sourced libs set nothing, which is correct for libraries (measured over `git ls-files '*.sh'`). E.g. `claude-code/hooks/security-static-check.sh:38`. **Change:** align, or relax the skill to `-euo` where no ERR trap is used. The rule and the code must agree |
| ShellCheck | CI runs default ShellCheck on all `.sh` (`security.yml:22-23`); clean today (measured rc=0) | Google: ShellCheck "is recommended for all scripts, large or small" (https://google.github.io/styleguide/shellguide.html). Optional checks `check-extra-masked-returns` and `check-set-e-suppressed` target exactly the BashFAQ/105 traps (https://github.com/koalaman/shellcheck/wiki/Optional; `shellcheck --list-optional` 0.11.0) | **Strength**, with one cheap upgrade. **Add** a `.shellcheckrc` with `enable=check-extra-masked-returns,check-set-e-suppressed`. Today that flags SC2312=75 and SC2310=4 (measured), the real masked-error sites. Skip the style-only options (`require-variable-braces` = 419 hits, `require-double-brackets` = 162) |
| stderr for diagnostics | `log()` to stderr; data to stdout (`SKILL.md:24-25`; `references/bash.md:13`) | Google: "All error messages should go to STDERR" | **Strength** |
| Function headers | Globals/Arguments/Outputs/Returns (`references/bash.md:20`) | Google: required for any function "not both obvious and short", and for every library function | **Strength.** Not enforceable mechanically |
| Script size | Hooks and installers are Bash | Google: shell is for "small utilities or simple wrapper scripts"; over 100 lines, "rewrite it in a more structured language" | **Trade-off.** 13 of 24 `.sh` exceed 100 lines (`scripts/install.sh` 543, `claude-code/hooks/lib/aa-ma-parse.sh` 336, `security-static-check.sh` 221; measured). | Indentation | 4 spaces in hooks (e.g. `security-static-check.sh:42-49`) | Google: "Indent 2 spaces. No tabs" | **Keep.** PEP 8: "Consistency within a project is more important" (https://peps.python.org/pep-0008/). Optionally pin with `shfmt -i 4` |
| Silencing | `\|\| true` / `2>/dev/null` need a `# why:` (`references/bash.md:25-30`) | (No external standard is this specific) | **Strength.** Unenforced: `security-static-check.sh:118,139` use `2>/dev/null`/`\|\| true` with no `# why:`. Enforce with a grep check in bats or CI on added lines |

### 5. Design principles

| Ours (cite) | Best practice / published critique (cite) | Verdict |
|---|---|---|
| **DRY**: "extract shared logic; document why duplication is intentional" (`claude-code/rules/engineering-standards.md:88-89`) | Dave Thomas: "Most people take DRY to mean you shouldn't duplicate code. That's not its intention"; DRY is about knowledge having "one authoritative, unambiguous representation" (https://www.artima.com/articles/orthogonality-and-the-dry-principle). Metz: "duplication is far cheaper than the wrong abstraction"; the remedy is to inline it back into every caller (https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction) | **Change** the wording to "one authoritative source per *fact* (schema, grammar, constant, count). Tolerate code duplication until the third occurrence (rule of three); prefer duplication to a parameter-and-conditional abstraction". The repo already does knowledge-DRY well (grammar SSoT `src/aa_ma/grammar.py`, regenerated counts) |
| **KISS**: "complexity requires justification recorded in context-log" (`:86-87`) | Fowler: YAGNI's costs are build, delay, carry and repair. It "only applies to capabilities … not … effort to make the software easier to modify" (https://martinfowler.com/bliki/Yagni.html) | **Add YAGNI** explicitly, with Fowler's scope limit (refactoring and tests are not YAGNI violations). KISS alone does not stop speculative features |
| **SOLID**: "single responsibility per module; depend on abstractions; favor composition" (`:90-91`) | Dan North (2022): SRP "creates artificial seams" and may be "a premature optimization"; he proposes properties, not principles: Composable, Unix philosophy, Predictable, Idiomatic, Domain-based (https://dannorth.net/blog/cupid-for-joyful-coding/) | **Keep, softened:** "depend on abstractions" *where a second implementation or a test seam exists*. In a small Python codebase, unconditional DIP creates the wrong abstractions Metz warns about |
| **SoC** (`:92-93`), **TDD** (`:83-85`) | (No credible current counter-guidance found; Fowler names self-testing code an enabling practice for evolutionary design, same YAGNI page) | **Keep** |
| **Prototype first** (`:21`) | Anthropic: "Build evaluations first … solving actual problems rather than anticipating requirements" (best-practices) | **Keep.** It is consistent with the eval-first guidance for skills |
